AWorkspaces por rama + Deployment pipelines

Construir una vez y promover: el contenido validado en Dev viaja a Test y Prod dentro de Fabric.

Rama de trabajo + workspace aislado→PR + checks→Merge→Update from Git (Dev)→Deployment pipeline Dev → Test → Prod

Encaja cuando

  • Prefieres la experiencia nativa de Fabric y poco código de despliegue.
  • Usas Git solo para desarrollo y quieres comparar etapas y ver el historial de despliegues dentro de Fabric.
  • Las reglas de despliegue y el autobinding bastan para la configuración por ambiente.

Ten presente

  • Estructura lineal (2 a 10 etapas); el número y los nombres de las etapas no cambian después de crear el pipeline.
  • No copia datos, permisos ni ajustes del workspace.
  • Git solo llega hasta Dev: Test y Prod se alimentan del workspace anterior.

BDespliegue basado en Git con fabric-cicd

Una carpeta del repo, un workspace por ambiente: tu CI publica un commit o tag concreto.

Rama de trabajo + workspace aislado→PR + checks→Merge / tag→fabric-cicd → Test→Aprobación→fabric-cicd → Prod

Encaja cuando

  • Quieres el repo como fuente de verdad y de todos los despliegues, con releases por tag.
  • Necesitas parametrizar por ambiente o ejecutar scripts/pruebas de build antes de publicar.
  • Tienes muchos workspaces destino (por ejemplo, uno por cliente).

Ten presente

  • Despliegue completo en cada ejecución (sin diffs) y solo para tipos de ítem soportados por la librería.
  • Las conexiones no están bajo control de código: se crean por ambiente.
  • La documentación indica que fabric-cicd no soporta deployment plans.

Dónde encaja Terraform

Terraform no es una tercera estrategia de promoción: aprovisiona la plataforma (workspaces, asignación de capacidad, roles con grupos de Entra y la conexión workspace ↔ Git). El contenido (notebooks, pipelines, modelos) viaja por A o por B.

Criterio del taller: define un único dueño por recurso. Si Terraform gestiona un ítem, no lo gestiones también por Git/fabric-cicd.
