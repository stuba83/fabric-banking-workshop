Honestidad técnica: las reglas del proyecto guían al agente, pero no son un control técnico. El control real son los permisos de tu identidad (rol en el workspace, acceso a la capacidad), la aprobación de comandos de terminal en VS Code y la revisión del diff en Git. Usa las tres capas juntas.
Los guardarraíles y dónde se ven en la demo

1 · Alcance de workspaces

Las reglas nombran el prefijo donde el agente puede crear o modificar (ws-ia-dev*) y listan lo que nunca debe tocar (laboratorios y demos de otros equipos).

Se ve en: Prompt 0 (en vivo).

2 · Datos sintéticos

El notebook genera los datos; el agente no lee ni copia datos de clientes. Es lo que permite practicar sin riesgo.

Se ve en: Prompt 1.

3 · Aprobación humana de la especificación

El skill de reportes escribe una especificación (_brief/report-spec.md) y se detiene. Nada se construye ni se publica hasta que una persona aprueba.

Se ve en: Prompt 5 → 6.

4 · Sin operaciones de capacidad

El agente no pausa, reanuda, escala ni borra la capacidad. Una persona confirma que está activa antes de la sesión y no la toca durante la demo.

Se ve en: verificación previa.

5 · Cambios revisables en Git

Modelos (TMDL) y reportes (PBIR) son archivos de texto en models/ y reports/: cada edición es un diff que se revisa o se revierte.

Se ve en: git diff --stat tras el Prompt 4.

6 · Identidad explícita

Antes de llamar a Azure o Fabric, el agente verifica la cuenta con az account show y no ejecuta az login ni az account set si no se lo piden.

Se ve en: Prompt 0.

Ejemplo genérico de reglas (.github/copilot-instructions.md)

El archivo es para el agente, por eso va en inglés. Adáptalo a tu entorno; los nombres son ficticios.

# AI-assisted Fabric development (synthetic data only)

## Before any Fabric or Azure call
- Run `az account show --query "{user:user.name,tenant:tenantId}" -o json` and confirm the account and tenant are the expected ones. If not, stop and tell the user.
- Never run `az login`, `az account set` or change any Azure CLI setting unless the user asks.
- Use the Fabric skills in `.github/skills` (and `.github/common`) for every Fabric task.

## Scope and safety rails
- Run every command in PowerShell. Do not use WSL.
- Create or modify items only in workspaces named `ws-ia-dev*`. Never touch any other workspace.
- Never pause, resume, scale or delete the Fabric capacity.
- Synthetic data only. Never read or copy customer data.
- Keep semantic models (TMDL) and reports (PBIR) as files in this repo so every change is a Git diff.
- For reports: write a spec first, show it, and wait for explicit approval before building or publishing.
- Prefer the local `powerbi-authoring-local` MCP server. Do not enable a second Power BI authoring server.

## Validated in this environment (replace with your own findings)
- Direct Lake: use the lakehouse SQL endpoint variant (the OneLake variant failed to refresh in our rehearsal).
- First use of the Authoring MCP: ask the user to review and accept the EULA; accept it only after the user explicitly authorizes it.
Cuidados aprendidos en el ensayo
La autenticación de la terminal verificar antes de la demo
Síntoma

El agente dice estar firmado con otra cuenta o tenant, o az falla con «subscription not found». Pasa con una terminal restaurada, con un perfil de Azure CLI distinto o al usar un shell de WSL.

Qué hacer

Abre una terminal PowerShell nueva dentro del proyecto y ejecuta az account show. Si el proyecto usa un perfil aislado de Azure CLI, la regla indica cómo restablecer la variable AZURE_CONFIG_DIR en esa terminal. No ejecutes az login salvo que el token haya expirado (lo hace una persona).

Frase

«El agente no se autentica solo: usa la sesión de mi terminal, y por eso lo primero que hace es comprobar quién es.»

EULA del servidor MCP en el primer uso verificar antes de la demo
Síntoma

El servidor MCP de autoría bloquea todas las llamadas hasta aceptar el EULA. En el ensayo no estaba aceptado y el agente escribió el TMDL a mano, sin usar el MCP.

Qué hacer

Una persona revisa el EULA y autoriza la herramienta accept_eula. Para ejecución desatendida existen --accepteula o PBI_MODELING_MCP_ACCEPT_EULA=true, solo después de revisarlo. Comprueba con «MCP: List Servers» que el servidor está iniciado.

Frase

«Aceptar el EULA es una decisión humana; el agente la ejecuta solo si yo lo autorizo.»

Qué skill elegir: despliegue vs. sincronización Git corregir si pasa
Síntoma

El agente carga deployment-pipelines-authoring-cli (promoción dev/test/prod) o git-integration-operations-cli (sincronizar workspace con Git) cuando querías un pipeline de datos o archivos locales.

Qué hacer

Detén al agente y repite la frase explícita: «(not a deployment pipeline)» o «do not use Fabric Git integration». Los prompts 2 y 3 ya la incluyen. Es una buena lección: el prompt también enruta el skill.

Frase

«Si elige mal, no es un fallo del flujo: es la señal para ser más específico y volver a pedirlo.»

Direct Lake sobre el endpoint SQL observado en un ensayo
Qué se observó

La variante Direct Lake sobre OneLake, creada por API, falló en el refresh («source tables do not exist or access was denied»); la variante sobre el endpoint SQL del lakehouse funcionó. La regla del proyecto la fija. En lakehouses con esquemas, el endpoint REST de «tables» no se admite: lista las tablas por OneLake o por el endpoint SQL.

Qué hacer

Si el refresh falla, es justo para lo que sirven el validador y el agente: volver a la variante del endpoint SQL. Es una observación de un entorno concreto, no una regla general: verifícala en el tuyo.

El reporte completo no cabe en una demo de 8 minutos tiempo observado

En un ensayo, armar y publicar el reporte llevó cerca de 23 min de tiempo de agente, con aprobación humana de la especificación. Es un tiempo observado en un ensayo, sin línea base manual: no es una cifra de beneficio. Por eso se muestra prearmado.

Sin Power BI Desktop no hay vista previa local

El agente puede validar y publicar el PBIR sin Desktop, pero sin él no hay capturas locales: la verificación visual se hace en el servicio, tras publicar.

7 · Licencias: tres «Copilot» distintos

GitHub Copilot este flujo

Suscripción de GitHub (planes Free, Student, Pro, Pro+, Max, Business y Enterprise según la documentación de GitHub). Es lo que usa el agente en VS Code o Copilot CLI. En cuentas de organización, algunas capacidades las controla una política del administrador de GitHub: por ejemplo, «MCP servers in Copilot» viene deshabilitada por defecto en cuentas enterprise.

Copilot en Fabric y Power BI otra pista

Experiencias dentro de Fabric. La documentación indica que está habilitado por defecto en tenants con capacidades de pago F2 o superior y que consume capacidad. Varias funciones, como Copilot en notebooks, están en vista previa.

Microsoft 365 Copilot otro producto

Copilot en las apps de Microsoft 365. La documentación indica que sus experiencias difieren en datos, integración y licenciamiento respecto de otros Copilot.

Regla práctica: tener uno no habilita los otros. Confirma el licenciamiento de cada uno con su administrador antes de comprometer una fecha.
